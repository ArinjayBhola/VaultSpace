# Security review and operating assumptions

This is a code review record, not a penetration-test or production-readiness certificate. Service configuration became available late; only read-only cloud health checks were performed. No live production security test or deployment was performed.

## Implemented controls

- Database singleton owner constraint; disabled Better Auth signup; CLI-only owner provisioning; library password hashing; database-backed sessions; secure production cookies; logout, password change and revocation.
- Server session validation in page layouts and independent route handlers. Anonymous API access fails before touching the database when no cookies exist. Public share grants authorize only their explicitly shared file; file operations require the owner session and trusted origin.
- Origin checks on application mutations, Better Auth's origin/CSRF handling on auth endpoints, Zod input schemas, 256 KiB application JSON limits, parameterized SQL, allowlisted sorting and bounded pagination.
- Database-backed login throttling. Vercel's trusted client-address header is selected in production. Public share authorization has a durable per-share 20-attempt/minute budget rather than trusting arbitrary client headers.
- Private R2 originals. Uploads use random staging IDs, short-lived PUT/part signatures, independently verified size and file signatures, ETag-conditional server copy, and a database lock around final copy/finalization. A still-valid staging PUT cannot overwrite an accepted original. Failed distributed operations remain tracked for cleanup.
- General file uploads are accepted within the configured name/size policy. MIME hints are normalized and bounded signature inspection identifies known formats; image, PDF and supported media MIME types require matching signatures before inline delivery. Other formats, including HTML, SVG and executables, are delivered as attachments. Text/JSON/Office previews render escaped content in the client, without executing scripts, macros or document links. Office ZIP/XML reads have compressed/expanded size and entry limits; external XML declarations are rejected. Downloads use safe encoded attachment names. PDF.js annotation links are disabled in the owner canvas reader.
- Five-minute HttpOnly share grants bound to one share; revalidation on every public byte request, including conditional 304 responses; 256-bit keyed pseudorandom bearer tokens stored only as SHA-256 hashes, plus versioned signed aliases bound to the same share ID and token hash; salted scrypt passwords; expiry and revocation; no owner metadata in public responses; private, mandatory-revalidation caching and no-referrer policies.
- Trashed resources are excluded from ordinary queries and public shares. Permanent cleanup deletes R2 bytes before relational metadata. Candidate deletion remains repeatable; missing objects are safe to delete again. Scheduled lifecycle cleanup and bucket lifecycle provide separate recovery paths.
- Activity logs avoid sensitive content and expire after 180 days. Terminal job diagnostics expire after 90 days; rate-limit rows after seven days. Owner download signatures last 90–120 seconds from issue, with redirect cache freshness capped at 60 seconds. Share streaming is separately authorized and does not expose a storage key.
- Owner originals and thumbnails can be stored in the browser's private HTTP cache for five minutes. Protected-folder bytes always revalidate the current session and ancestor unlocks; ordinary cached owner bytes can remain fresh until their TTL ends. All conditional responses authorize before checking the validator. Login/logout, security and access-changing file/folder mutations rotate an HttpOnly cache-revision cookie and request HTTP-cache clearing; Vary: Cookie prevents old cached variants from being reused without validation. Derived preview URLs include preparation generation and state. API metadata and errors remain no-store at the HTTP layer, with bounded client query caching. Already downloaded bytes cannot be withdrawn; cross-device changes take effect on the next required request.

## Release checks still required

Manually verify critical workflows against isolated Neon and R2 resources; verify cookies, rate limits, CSRF rejection, storage signatures, multipart failures, duplicate completion, range delivery and request-driven cleanup under failures. Browser rendering/accessibility and cross-browser PDF highlight behavior still need manual browser verification.

Verify Vercel log redaction for token-bearing paths and protect environment secrets and cloud dashboards. Confirm backups and recovery, dependency audit results, least-privilege R2 permissions and private bucket settings at deployment time.

There is no bundled OCR or malware scanner, no passkey/2FA integration, and no external security audit. For malware scanning, insert a quarantined scanning job before accepting a file for processing/sharing, record scanner verdict/version, and fail closed before granting access. This is an extension point, not a claimed feature.

Shared-viewer presence is authorized by an unexpired signed HttpOnly grant and a live, unrevoked share. Heartbeats validate origin and Zod input, are rate-limited per share, and store only a hash of the random tab identifier. Presence cannot be used to authorize file content. Valid open-page heartbeats renew a five-minute grant; expired grants require authorization again. Owner-only statistics exclude revoked/expired grants and stale heartbeats. Development request logging excludes token-bearing share and presence paths.

Request-based operations require owner authentication, trusted origin and validated JSON. PostgreSQL row locks and SKIP LOCKED claim work; expiring leases serialize each file across generations. PDF page progress is persisted in short batches and metadata is kept until storage cleanup succeeds. No unauthenticated job-provider endpoint or event/signing keys remain.

Single active sharing is enforced by a locked API check and a database trigger on creation/lifecycle updates. Versioned aliases for older hash-only shares are verified with constant-time HMAC comparison before granting access; passwords, expiry, revocation, file deletion and throttling apply identically to original URLs. URL recovery is owner-authenticated and no-store, and hashes are removed from the response. Revoking already-ended shares cannot reset their 24-hour display window. Concurrent request behavior has been reviewed but not load-tested.

Presence counts include authorized shared-page sessions with a real heartbeat in the last 90 seconds, including background tabs. Closed sessions retain a short-lived epoch-expiry tombstone so delayed heartbeat requests cannot resurrect them. Heartbeat updates renew expired liveness rows only while their request grant remains valid, and never renew a tombstone. Maintenance removes records without a heartbeat for five minutes. Existing password, revocation, expiry, origin, grant and rate-limit checks remain in force.
